# Backend gaps for the operations workspace

Verified against the checked-in admin API/client/contracts at baseline
`d1a14804c135037b43a3b945b84171ce634d87fe`. These are proposed follow-ups, **not existing
or approved API contracts**. No Uranus repository or live source database was inspected.
No backend implementation is included. Frontend code must not call the proposed paths.

| Desired feature                                             | Missing capability                                                  | Why / possible future read structure                                                                                                                                                                                                                                                           |
| ----------------------------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Social Posts, Targets and Publications                      | No admin read endpoints or corresponding schemas/proxy routes       | Separately reviewed, authenticated read endpoints such as `GET /api/v1/social/posts`, `/targets`, `/publications`, with bounded pagination and validated status filters                                                                                                                        |
| Publication diagnosis                                       | No platform/account/source/target/status/history projection         | A publication projection could include identifiers and display labels, publication source, fingerprint, remote post ID, `started_at`, `finished_at`, a safe error category and a redacted rendered snapshot; no credentials, tokens or raw provider errors                                     |
| Scheduling and stuck publishing                             | No status aggregates, trustworthy timing or worker observations     | A proposed summary could return `observed_at`, counts and oldest active timestamps. Verify actual source states before defining `draft`, `scheduled`, `publishing`, `published`, `failed`, `cancelled` or publication `uncertain`; duration thresholds require a documented operational policy |
| True activity diff                                          | Existing creation feed and timeline have no `before`/`after` values | A future bounded changes array could contain `field`, typed `before`, typed `after`, event timestamp and authorized actor display label, with secret-field exclusions. A last-updated timestamp is not change history                                                                          |
| Global latest changes                                       | Dashboard activity lists creations; timelines are per entity        | A reviewed cursor-paginated audit feed could provide event kind, entity identity, actor, time and verified navigation targets                                                                                                                                                                  |
| Timelines for event dates, memberships and partner requests | Timeline supports only six collection types                         | Extend the timeline contract only after validating source evidence and composite-key identity; retain unknown timestamps                                                                                                                                                                       |
| Entity-specific operational queues                          | Inbox/geocoding list cannot filter by entity key                    | Proposed exact `entity_type` + `entity_key` filters could expose bounded current workflow state. Do not download whole queues and filter the first page locally                                                                                                                                |
| Worker health                                               | Existing check-run status is not process/worker health              | A separately authenticated observed worker projection could provide last heartbeat, lease and queue age. Existing liveness/readiness endpoints do not establish this information                                                                                                               |
| Source actor resolution                                     | Timeline actor may be an admin subject rather than a display name   | A reviewed actor projection must distinguish admin and Uranus identities; never interpret `admin:<UUID>` as a Uranus user UUID                                                                                                                                                                 |

Any future contract requires a separate backend task and coordinated Pydantic,
Zod, client, Nitro, OpenAPI and regression-test changes. The current workspace
shows explicit unavailable states and only uses existing read contracts.
